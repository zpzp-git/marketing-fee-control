# 营销费控系统 Demo 全局开发说明

## 1. 文档定位

本文用于指导营销费控系统 mock demo 的页面设计评审、前端实现、mock 数据组织、演示闭环设计和验收检查。

当前阶段目标不是建设完整生产系统，而是基于已有页面详细设计，做出“能闭环、能演示、能跑通”的前端 Demo。

参考资料：

- 整体规划：`docs/prd/00-营销费控系统-demo整体规划.md`
- 页面详细设计：`docs/prd/页面详细设计/`

## 2. 开发阶段边界

### 2.1 当前只做 mock demo

本阶段只实现前端可演示能力：

- 页面路由、布局、导航、列表、表单、详情、弹窗、抽屉、审批流展示。
- mock 数据查询、筛选、分页、新增、编辑、提交、审批、变更、关闭等前端状态变化。
- 单据与台账之间的关键联动，用本地 mock 数据或内存状态模拟。
- 关键业务状态、金额、单号、同步状态、失败原因、审批记录可展示、可变化。

不实现完整生产能力：

- 不做真实后端服务。
- 不做真实数据库。
- 不做真实登录鉴权、组织权限、数据权限。
- 不做真实流程引擎。
- 不做真实财务凭证、银行支付、发票查验、ERP 过账。
- 不追求所有字段规则 100% 工程化实现。

### 2.2 技术栈固定

技术栈固定为：

- Next.js
- React
- TypeScript
- Tailwind CSS

不要建议更换技术栈，不引入与 Demo 目标无关的复杂框架。组件、状态、mock 数据和路由实现应优先匹配当前项目已有结构。

## 3. 页面实现原则

### 3.1 高度参考原始详细设计

每个页面实现前应先阅读对应 md：

1. 优先还原原始页面的业务对象、字段、分区、按钮、列表列、表单区块、审批区、台账规则。
2. 字段名称、单据名称、台账名称尽量使用原文，避免随意改名。
3. 原始页面中的必填、只读、自动带出、关联台账、显示/隐藏规则，至少要在核心流程中体现。
4. 对复杂表格和单据，优先保留核心字段和关键业务规则，非核心字段可折叠、简化或放入“更多信息”区域。

### 3.2 允许合理补齐

如果原始 md 中存在以下情况，可以按成熟 B 端后台系统规范合理补齐：

- Excel 转 md 后字段识别不准、表头错位、重复列较多。
- 流程图识别不完整。
- 操作按钮缺失。
- 详情页、审批记录、异常原因、空状态说明缺失。
- 筛选项、状态枚举、列表操作不完整。
- 单据和台账之间缺少演示所需的中间状态。

补齐时遵循：

- 不改变原始业务含义。
- 不引入真实外部集成。
- 不扩展成生产级复杂流程。
- 优先补齐 B 端后台常见能力：查询、重置、新增、编辑、详情、提交、审批、驳回、撤回、关闭、导出模拟。

## 4. 第三方与外部系统处理

所有第三方系统、外部平台、银行、ERP、广告平台、电商平台、OA、审批系统、支付、短信、发票查验等，均不做真实集成。

Demo 中只允许使用 mock 数据和前端状态模拟：

- 来源系统：如 ERP、OA、银行、广告平台、电商平台、发票平台。
- 同步状态：未同步、同步中、同步成功、同步失败。
- 最近同步时间。
- 同步批次号。
- 失败原因。
- 操作反馈：如“已发起同步”“同步失败，可重试”“已模拟推送审批”。

外部操作按钮可以保留，但必须是模拟行为：

- “同步 ERP”：更新同步状态和最近同步时间。
- “发起审批”：生成审批记录并切换单据状态。
- “支付确认”：模拟支付成功或失败。
- “发票查验”：模拟查验通过、查验失败或待查验。
- “平台账单导入”：使用内置 mock 文件/数据生成列表记录。

## 5. 模块闭环要求

每个模块至少形成一个可演示业务闭环。闭环不要求覆盖所有页面，但必须能说明该模块的主要业务价值。

| 模块 | Demo 闭环建议 |
|---|---|
| 基础数据 | 查看台账 -> 新增/变更费用类型、营销活动或账户 -> 提交 -> 审批通过 -> 台账状态更新 |
| 预算管理 | 查看预算 -> 编制/调整预算 -> 提交审批 -> 审批通过 -> 预算台账占用/可用金额变化 |
| 营销备用金 | 备用金申请 -> 审批通过 -> 报销核销 -> 专项备用金台账更新 |
| 保证金管理 | 保证金付款申请 -> 审批通过 -> 保证金台账生成 -> 退回申请 -> 台账关闭 |
| 营销事项 | 新建营销事项 -> 提交审批 -> 事项台账生成 -> 费用使用 -> 费用台账更新 |
| 应收账款 | 查看应收/坏账数据 -> 发起坏账申请或计提 -> 审批 -> 状态和金额更新 |
| 营销计划 | 新建营销计划 -> 关联活动/渠道/达人 -> 提交 -> 计划状态更新 |
| 营销合同 | 新建合同 -> 结构化复核 -> PO 执行单 -> 合同台账更新 |
| 发票管理 | 发票核销/红冲/无票申请 -> 审批 -> 发票核销台账或待到票台账更新 |
| 内部领用 | 新建内部领用 -> 审批 -> 台账生成 -> 状态关闭 |
| 付款管理 | 对公付款/预付款/投放充值 -> 提交审批 -> 模拟支付 -> 付款台账更新 |
| 费用预估 | 查看费用预估台账 -> 生成/调整预估 -> 预提或摊销状态更新 |
| 其他损益 | 新建损益确认/预提单 -> 审批 -> 损益台账更新 |
| 费用对账结算 | 导入/查看账单 -> 自动对账 -> 差异处理 -> 结算单生成 |
| 销售合同 | 合同结构化 -> 结算单 -> 返利计提 -> 台账状态更新 |

## 6. 页面状态要求

每个核心页面至少考虑以下状态：

- normal：有数据、可操作、可筛选、可查看详情。
- loading：进入页面、切换筛选、提交操作时有加载反馈。
- empty：无匹配数据时展示空状态和下一步动作。
- error：模拟接口失败、同步失败、提交失败时展示原因和重试入口。

建议实现方式：

- 列表页支持筛选触发 loading，筛选无结果进入 empty。
- 详情页支持“模拟加载失败”或通过 mock 状态展示 error。
- 表单提交失败时展示字段校验、业务校验或外部模拟失败原因。
- 第三方同步失败必须展示失败原因和重试按钮。

## 7. 交互与业务规则取舍

Demo 阶段优先实现能被演示感知的规则：

- 必填校验。
- 金额不能小于等于 0。
- 本次付款金额不能超过应付余额、到票金额、预算可用金额等关键约束。
- 提交后状态从“草稿”变为“审批中”。
- 审批通过后状态变为“已生效”“已完成”或“已关闭”。
- 审批驳回后可编辑并重新提交。
- 台账金额、占用金额、已核销金额、同步状态随操作变化。

可以暂缓的规则：

- 复杂多级组织权限。
- 完整审批路由计算。
- 全量字段联动。
- 跨模块全链路金额精确平衡。
- 真实附件上传和解析。
- 真实导入导出。

## 8. Mock 数据规范

mock 数据应服务演示闭环，不追求生产完整性。

基础要求：

- 每个模块准备 8-20 条高质量样例数据。
- 每个列表至少包含 3 种业务状态。
- 金额、日期、单号、供应商、渠道、店铺、活动、预算科目要看起来真实可信。
- 数据之间尽量能串起来，例如合同、营销事项、付款、发票、台账使用相同的业务对象。
- 保留异常样例：同步失败、审批驳回、预算不足、待到票、部分核销。

建议统一字段：

- `id`
- `code`
- `name`
- `status`
- `amount`
- `applicant`
- `department`
- `createdAt`
- `updatedAt`
- `approvalStatus`
- `sourceSystem`
- `syncStatus`
- `lastSyncAt`
- `failureReason`

## 9. UI 风格规范

整体 UI 风格统一为现代 B 端 SaaS 后台：

- 清晰、稳重、可演示。
- 信息密度适中，适合业务人员和财务人员快速扫描。
- 列表页优先使用筛选区、数据表格、状态标签、行内操作。
- 表单页优先使用分组区块、必要字段、明细表、审批记录。
- 详情页优先使用摘要卡片、关键状态、基础信息、明细信息、流转记录。
- 颜色克制，状态色明确：成功、处理中、警告、失败、禁用。
- 不做营销落地页风格，不做过度装饰。

常用页面结构：

- 模块列表页：标题区 + 操作按钮 + 筛选区 + 表格 + 分页。
- 单据表单页：基础信息 + 业务信息 + 明细表 + 附件模拟 + 审批信息 + 底部操作。
- 详情页：状态摘要 + 只读字段 + 明细 + 关联单据 + 操作记录。
- 台账页：强筛选、强表格、弱编辑，突出状态、金额和来源。

## 10. Gemini 与 Codex 分工

### 10.1 Gemini 主要负责

- UI/UX 设计说明。
- 页面结构建议。
- 交互建议。
- 原始页面截图或视觉还原评审。
- 对复杂 Excel/流程图识别结果进行人工可读化整理。
- 检查页面是否符合现代 B 端 SaaS 后台体验。

Gemini 输出应尽量具体到页面区块、字段分组、关键交互、状态设计和视觉问题。

### 10.2 Codex 主要负责

- Next.js / React / TypeScript / Tailwind 代码实现。
- 项目路由、布局、导航、组件集成。
- mock 数据、前端状态、业务闭环模拟。
- 表单校验、列表筛选、详情页、弹窗、审批状态切换。
- 构建错误、类型错误、样式问题修复。
- 运行项目、构建检查和必要的代码验证。

Codex 实现时应优先复用项目已有组件和样式，不为单个页面创建过度抽象。

## 11. 开发执行顺序

建议按模块逐步开发，每个模块遵循以下顺序：

1. 阅读模块目录下页面 md 和流程图 md。
2. 确定本模块最小演示闭环。
3. 设计列表、表单、详情、审批/操作反馈的页面结构。
4. 准备 mock 数据和状态枚举。
5. 实现路由、页面、组件和交互。
6. 补齐 normal、loading、empty、error 状态。
7. 跑通新增、编辑、提交、审批、台账更新等关键动作。
8. 执行构建或类型检查，修复明显问题。
9. 用页面截图或本地预览检查 UI 是否稳定、清晰、可演示。

## 12. 验收标准

一个模块完成 Demo 开发，应满足：

- 页面名称、字段、业务对象与原始详细设计高度一致。
- 至少一个业务闭环能完整演示。
- 列表可筛选、可查看详情。
- 表单可新增或编辑，并有基础校验。
- 提交、审批、驳回、关闭等关键状态能前端模拟。
- 台账或关联数据能看到操作后的变化。
- 第三方集成全部为 mock，不发生真实外部调用。
- 核心页面具备 normal、loading、empty、error 状态。
- UI 风格统一，适合 B 端后台演示。
- `npm run build` 或项目约定检查能通过；如不能运行，需记录原因。

## 13. 重要约束

- 不因 Demo 需要引入真实外部系统账号、密钥、接口。
- 不把 mock 行为伪装成真实集成。
- 不为了少量页面创建复杂通用平台能力。
- 不随意改动原始 PRD 文档口径。
- 不忽略页面详细设计中的核心字段和台账规则。
- 不让页面只有静态展示，必须尽量可操作、可反馈、可闭环。
