# 3.7.5 营销事项管理模块实现说明

本文用于指导 Gemini 和 Codex 实现“营销事项管理”模块 Demo。不要按正式 PRD 重写，优先做出能演示、能闭环、能跑通的前端 mock 页面。

## 模块目标

营销事项管理模块用于承接营销计划、营销活动和预算占用，形成可追踪的营销事项，并在后续付款、备用金、个人垫付报销或发票核销完成后更新事项使用和关闭状态：

- 支持业务人员新建营销事项申请，填写事项名称、事项总额、关联营销计划、营销活动、预算部门、预算科目和归属打标等信息。
- 支持提交审批，审批通过后生成营销事项台账记录，并模拟占用预算。
- 支持在事项台账查看事项状态、总额、已用金额、活动金额、使用部门和预算科目。
- 支持查看营销事项费用台账，展示个人垫付报销等费用使用明细。
- 支持系统提醒未关闭事项，并允许手动发起营销事项关闭。
- 支持模拟对公付款、专项备用金、个人垫付报销、发票核销等外部流程完成后自动核销或关闭事项。

Demo 阶段重点是跑通“新建营销事项 -> 提交审批 -> 生成事项台账 -> 模拟费用使用 -> 更新费用台账和已用金额 -> 手动/自动关闭事项”的闭环，不做真实 OA、预算系统、付款、发票或第三方平台集成。

## Demo 业务闭环

优先实现 2 条可演示闭环：

1. 事项申请和台账生成闭环：业务人员新建营销事项申请 -> 填写营销事项名称、事项总额、营销活动明细、预算部门和预算科目 -> 提交时校验事项总额小于 5W 且等于营销活动金额合计 -> 模拟财务 BP 审批 -> 模拟业务领导审批 -> 审批通过后新增营销事项台账，事项状态为“未使用”或“进行中”，提醒日期为申请日期 + 3 天，并模拟预算占用。
2. 费用使用和事项关闭闭环：在营销事项台账选择一条生效事项 -> 点击“模拟费用使用”生成个人垫付费用台账记录 -> 回写实际核销金额/已用金额 -> 已用金额等于事项总额时自动关闭，或由系统提醒后手动发起营销事项关闭单 -> 审批通过后事项状态变为“已关闭/完结”。

跨模块流程只做 mock 演示：

- 对公付款流程完成后，模拟核销营销事项。
- 专项备用金流程完成后，模拟核销营销事项。
- 个人垫付报销流程完成后，写入营销事项费用台账。
- 发票到票核销完成后，模拟更新事项已用金额。
- 定期巡查未关闭事项时，展示提醒状态和“关闭营销事项”入口。

## 主要字段建议

通用单据字段：

- 单据编号、单据名称、申请日期、申请人、申请人公司、申请人部门、申请人岗位。
- 单据状态：草稿、审批中、已驳回、审批通过、已生效、关闭审批中、已关闭。
- 审批信息：行号、流程环节名称、审批人、审批日期、审批意见。
- 附件信息：附件名称、附件类型、上传人、上传时间，附件只做 mock。

营销事项申请单字段：

- 主表区：营销事项名称、营销事项总额、说明。
- 申请信息明细：行号、关联营销计划、营销活动计划分类、营销活动、预算部门、预算科目、归属打标、计划剩余金额、营销活动金额。
- 自动带出：申请日期、申请人、申请人公司、申请人部门、申请人岗位、预算科目。
- 关键规则：营销事项名称必填；营销事项总额必填且大于 0；Demo 以小于 50000 为可提交；营销事项总额必须等于明细行营销活动金额合计；营销活动、预算部门、预算科目、营销活动金额必填。
- 部门规则：申请人部门隶属于品牌运营中心时，关联营销计划、营销活动计划分类、计划剩余金额显示且必填；申请人部门隶属于品牌产品中心时，归属打标显示且必填。
- 预算规则：预算科目由营销活动属性自动带出；预算部门可由组织机构映射预算组织，也可在 Demo 中允许下拉修正。

营销事项关闭单字段：

- 主表区：申请日期、申请人、申请人公司、申请人部门、申请人岗位。
- 关闭信息：营销事项名称、营销事项总额、营销活动金额、使用部门、营销活动类型、营销活动名称、一级预算科目、二级预算科目、营销事项申请说明、营销事项关闭说明。
- 关键规则：关闭信息从营销事项台账自动带出，只读展示；营销事项关闭说明可编辑；没有绑定进行中业务单据或已完成费用核销的事项才允许关闭。

营销事项台账字段：

- 申请人姓名、营销事项名称、营销事项状态、营销事项总额、实际核销金额/已用金额、营销活动类型、营销活动名称、营销活动金额、使用部门、预算科目。
- 建议补齐：事项编号、申请单号、申请日期、提醒日期、预算部门、一级预算科目、二级预算科目、关联营销计划、计划分类、已占用预算、剩余可用金额、是否发票个人垫付核销、关闭单号、最近使用日期、同步状态、失败原因。
- 状态建议：未使用、进行中、待关闭、关闭审批中、已关闭、已驳回。

营销事项费用台账字段：

- 单据编号、单据名称、申请日期、申请人、费用日期、费用金额、营销活动、费用小类、费用大类、二级预算科目、一级预算科目、经分科目、品牌。
- 建议补齐：营销事项编号、营销事项名称、来源业务类型、来源系统、核销状态、核销日期、供应商/收款人、使用部门、备注。

## 关键交互

- 列表页统一支持查询、重置、分页、导出模拟、详情抽屉。
- 营销事项申请单支持保存草稿、提交审批、撤回、审批通过、审批驳回。
- 申请信息明细支持新增/删除行，营销活动金额合计实时回写或校验营销事项总额。
- 选择关联营销计划后，带出营销活动计划分类和计划剩余金额；选择营销活动后，带出预算科目、费用分类、经分科目和品牌。
- 提交申请时校验必填、金额大于 0、事项总额小于 50000、事项总额等于活动金额合计、营销活动金额不超过计划剩余金额或预算可用金额。
- 审批通过后新增营销事项台账记录，写入提醒日期、事项状态、申请金额、营销活动、预算部门、预算科目，并模拟预算占用。
- 台账行内支持“详情”“模拟费用使用”“关闭营销事项”；已关闭事项不允许再次关闭。
- 点击“模拟费用使用”弹出小表单，填写费用日期、费用金额、费用小类、来源业务类型；确认后新增费用台账记录，并更新事项实际核销金额/已用金额。
- 当已用金额等于或超过营销事项总额时，事项可自动变为待关闭或已关闭；Demo 可提供开关或按钮演示自动关闭。
- 系统提醒未关闭事项：提醒日期 <= 当前日期且状态不是已关闭时，台账显示提醒标签，并在详情中显示提醒原因。
- 手动关闭事项时，从台账带出关闭信息；若存在审批中付款、报销或核销 mock 单据，阻止关闭并展示原因。
- 关闭申请审批通过后，营销事项台账状态更新为已关闭，写入关闭单号和关闭说明。
- 费用台账支持按营销活动、费用小类筛选；点击来源单据只打开 mock 详情，不跳真实外部系统。

## 第三方系统处理方式

- OA 审批、预算系统、营销计划系统、对公付款、专项备用金、个人垫付报销、发票核销、ERP/金蝶凭证全部 mock。
- 保留外部动作按钮，但只更新前端状态和操作记录：
  - “模拟提交 OA”：单据状态变为审批中，生成审批节点。
  - “模拟审批通过/驳回”：切换审批状态，记录审批人、审批日期和意见。
  - “模拟占用预算”：更新事项的预算占用状态和预算占用金额，不调用真实预算服务。
  - “模拟个人垫付报销完成”：新增费用台账记录，更新已用金额。
  - “模拟对公付款完成”：新增费用使用记录或直接更新实际核销金额。
  - “模拟发票核销完成”：更新核销状态和费用台账来源信息。
  - “模拟关闭巡检”：把超提醒日期未关闭事项标记为待关闭并生成提醒记录。
- 所有外部同步字段建议保留：来源系统、同步状态、最近同步时间、同步批次号、失败原因。
- 不连接真实 OA、预算系统、ERP、付款系统、发票平台、营销计划系统，不上传或解析真实附件。

## UI/UX 重点

- 整体按 B 端财务运营后台设计，突出事项状态、金额、预算科目、已用金额和关闭风险。
- 单据页使用分组区块：基础信息、申请信息明细、附件模拟、审批信息、操作记录。
- 事项总额、营销活动金额、实际核销金额、剩余金额统一右对齐、千分位展示。
- 营销事项状态使用清晰状态标签：未使用为默认，审批中/进行中/关闭审批中为处理中，已关闭为成功，已驳回/同步失败为失败，待关闭为警示。
- 申请信息明细表是核心区域，建议固定行号、营销活动、营销活动金额、预算科目等关键列。
- 品牌运营中心和品牌产品中心的动态字段要有稳定布局，避免字段显示隐藏导致页面大幅跳动。
- 台账页以查询和详情为主，行内操作克制；关键操作“关闭营销事项”应有二次确认。
- 费用台账强调来源单据和费用分类，适合横向滚动；关键列建议固定：单据编号、费用日期、费用金额、营销活动、费用小类。
- 空状态提供“新建营销事项”或“重置筛选”；错误状态提供“重试模拟同步”。
- 附件只展示文件名和上传状态，可保留上传入口但不做真实文件解析。

## 验收标准

- 页面名称、核心字段、表单分区、台账列和流程节点与原始详细设计保持一致。
- 至少跑通“营销事项申请 -> 审批通过 -> 事项台账生成 -> 模拟费用使用 -> 费用台账更新 -> 事项关闭”的闭环。
- 营销事项申请单可保存、提交、审批通过、审批驳回，并有基础必填和金额校验。
- 提交时能校验营销事项总额小于 50000，且营销事项总额等于营销活动金额合计。
- 审批通过后能新增事项台账记录，并体现预算占用、提醒日期和事项状态。
- 台账可按营销事项名称、使用部门查询，支持重置、导出模拟、详情查看和发起关闭。
- 费用台账可按营销活动、费用小类查询，能展示个人垫付等 mock 来源费用。
- 关闭单能从台账带出事项信息，填写关闭说明，审批通过后更新事项状态。
- 外部系统行为全部为 mock，不发生真实 OA、预算、付款、发票、ERP 或附件上传调用。
- 核心页面具备 normal、loading、empty、error 或失败提示状态。
- UI 风格统一、稳定，适合现场演示。
- 开发完成后执行项目约定检查，优先 `npm run build`；如无法执行，记录原因。
