# 3.7.13 付款管理模块实现说明

本文用于指导 Gemini 和 Codex 实现“付款管理”模块 Demo。不要按正式 PRD 重写，优先做出能演示、能闭环、能跑通的前端 mock 页面。

## 模块目标

付款管理模块用于承接合同、结算、发票、无票、营销事项和投放账户等业务结果，完成付款申请、预付款申请、投放账户充值、退款/退票重付以及相关台账更新：

- 支持对公付款申请，覆盖有合同已发票核销、有合同未发票核销、无票付款、无合同关联营销事项/计划等场景。
- 支持供应商对公预付款申请，审批通过后形成供应商预付款台账，并模拟更新合同履约区。
- 支持投放账户充值申请，审批和财务付款后更新投放账户余额台账、投放账户明细台账。
- 支持投放充值退款和退票重付的异常付款闭环。
- 支持供应商应付账款台账、供应商预付款台账、投放账户余额/明细台账查询、详情和导出模拟。

Demo 阶段重点跑通“申请单 -> 提交审批 -> 模拟支付/审批通过 -> 台账更新”的闭环，不接真实银行、CBS、ERP、OA、广告平台或资金流水系统。

## Demo 业务闭环

优先实现 4 条可演示闭环：

1. 对公付款闭环：从供应商应付账款台账选择一条“待付款/部分付款”记录 -> 发起对公付款申请 -> 自动带出核算主体、供应商、合同编号、结算单号、应付日期、应付金额、应付余额 -> 填写本次付款金额和付款信息 -> 提交审批时应付台账核销中金额增加 -> 模拟审批通过和付款成功 -> 累计已付款金额增加、应付余额减少、生成凭证号和操作日志。
2. 预付款闭环：新建对公预付款申请 -> 选择合同和付款阶段 -> 自动带出合同名称、合同类型、付款金额、付款比例、预计付款时间和收款账号 -> 提交审批时合同履约区占用金额增加 -> 审批通过后生成供应商预付款台账，核销状态为“未核销”、是否到票为“否”，合同履约区已用金额增加。
3. 投放充值闭环：新建投放账户充值申请 -> 选择平台协议和投放账户 -> 填写多行充值金额、预期充值日期、付款链接 -> 预充值总金额自动汇总 -> 财务填写实际付款金额和实际支付日期 -> 审批通过后更新投放账户余额台账预充值总金额，插入投放账户明细台账；如实际付款金额与充值金额合计不一致，标记“存在充值差异”。
4. 异常重付闭环：模拟一条支付失败记录 -> 发起退票重付申请 -> 带出原支付建议号、付款方式、原收款对象和付款金额 -> 填写退票原因、变更后收款对象/账号 -> 提交审批 -> 模拟重付成功后原支付状态变为“已重付”，新支付记录变为“支付成功”。

可选演示闭环：

- 无票付款：对公付款单选择“是否无票=是”，关联无票核销申请台账，审批通过后无票台账占用释放、已用金额增加。
- 未发票核销付款：对公付款单选择待到票台账结算记录，本次付款金额不得大于到票金额，审批后更新待到票状态。
- 投放充值退款：从投放账户余额台账发起退款申请，退款金额不得超过充值余额，审批后余额台账退款金额增加。
- 财务驳回：审批中单据被驳回后释放核销中/占用金额，回到可编辑状态。

跨模块数据只做 mock 串联：

- 合同、付款阶段、合同履约区来自营销合同管理 mock。
- 应付账款可来自发票核销台账、待到票台账或费用结算 mock。
- 无票数据来自发票管理无票核销申请台账 mock。
- 营销事项、预算科目、投放账户、平台协议、供应商账户均来自本地 mock。

## 主要字段建议

对公付款申请单主表区：

- 单据编号、申请日期、申请人、申请人公司、申请人部门、申请人岗位。
- 核算主体、供应商、凭证号、是否有合同、是否无票、是否已发票核销、合同编码、本次付款合计、预付款余额、说明。

- 主表区：单据编号、申请日期、申请人、结算主体/核算主体、供应商、凭证号、退票原因、营销事项、合同名称、合同编码、付款合计金额、说明。
- 付款区：支付建议号、付款方式、原收款对象、原收款银行账号、收款开户名、收款银行、收款支行、支付建议状态、付款金额、变更后收款对象、变更后收款账号、实际支付日期。

台账字段：

- 供应商应付账款台账：单据编号、单据名称、合同编号、核算主体、供应商、应付日期、应付金额、核销中金额、累计已付款金额、应付余额、结算单号、申请人部门、创建人、付款状态。
- 供应商预付款台账：单据编号、核算主体、供应商、合同名称、合同编号、预付总金额、核销中金额、已核销金额、未核销金额、核销状态、是否到票、申请人部门。
- 投放账户余额台账：单据编号、投放平台、核算主体、投放账户、品牌、供应商、预充值总金额、实际消耗金额、充值余额、现金余额、退款金额、累计已到票金额、累计未到票金额。
- 投放账户明细台账：单据编号、投放账户、投放账户 ID、投放平台、核算主体、营销活动、充值金额、实际付款金额、充值差异金额、是否存在过充值差异、审批状态。

状态枚举：

- 单据状态：草稿、审批中、已驳回、审批通过、待付款、支付中、支付成功、支付失败、已完成、已关闭。
- 应付状态：待付款、付款中、部分付款、已付款、已关闭。
- 预付核销状态：未核销、核销中、部分核销、已核销。
- 到票状态：否、到票中、部分到票、是。
- 投放充值状态：待充值、充值中、充值成功、存在差异、已退款。
- 同步状态：未同步、同步中、同步成功、同步失败。

关键规则：

- 金额必须大于 0；本次付款合计等于付款区付款金额合计。
- 对公付款选择“有合同、无票=否、已发票核销=是”时，必须关联供应商应付账款台账，本次付款金额不得大于应付余额。
- 对公付款选择“有合同、无票=否、已发票核销=否”或“无票=是”时，必须关联待到票/无票台账，本次付款金额不得大于到票金额或无票可用金额。
- 对公付款选择“无合同”时，必须关联营销事项申请或营销计划，审批通过后模拟更新预算发生数和营销事项费用台账。
- 预付款余额大于 0 时显示预付区；本次预付核销金额不得超过未核销金额。
- 对公预付款预付总金额等于合同信息区或营销事项信息区付款金额合计。
- 5 万以上预付款必须关联合同；5 万及以下无合同预付款必须关联营销事项申请，并展示附件必填提示。
- 投放充值预充值总金额等于投放账户信息区充值金额合计；充值差异金额=实际付款金额-充值金额合计。
- 投放退款金额不得大于对应投放账户充值余额。
- 退票重付必须选择原支付失败/退票记录，重付金额默认等于原付款金额。

## 关键交互

- 付款管理工作台顶部展示摘要指标：待付款金额、应付余额、预付未核销金额、投放充值余额、支付失败数、充值差异金额。
- 供应商应付账款台账支持按核算主体、供应商、合同编号、结算单号、应付日期、付款状态筛选；行内支持“发起付款”“详情”。
- 供应商预付款台账支持按供应商、核算主体、合同编号、核销状态、是否到票筛选；行内支持“详情”“关联付款核销”。
- 投放账户余额台账支持按投放平台、投放账户名称、核算主体、供应商筛选；行内支持“发起充值”“发起退款”“查看明细”。
- 对公付款单通过“是否有合同、是否无票、是否已发票核销”切换表单区块，隐藏不相关区块，保留关键必填提示。
- 弹窗选择应付、待到票、无票、预付款、营销事项时按核算主体和供应商过滤，避免跨供应商选择。
- 金额输入后实时刷新本次付款合计、应付余额、预付未核销金额、充值差异金额。
- 提交审批后生成审批记录，按钮切换为“模拟审批通过”“模拟驳回”“撤回”。
- 审批通过后进入待付款或支付中，点击“模拟支付成功”后回写实际支付日期、凭证号、支付建议号和台账金额。
- 支付失败时展示失败原因，如“收款账号已失效”“银行退票”“CBS 同步失败”，并提供“发起退票重付”入口。
- 投放充值财务付款区默认实际付款金额等于充值金额合计，允许财务修改以演示差异；差异不为 0 时显示醒目的差异提示。
- 导出、提交 OA、同步 CBS、银行付款、生成凭证、同步 ERP/金蝶全部只做前端反馈和状态更新。

## 第三方系统处理方式

- 银行、招行 CBS、OA、ERP、金蝶、广告平台、合同系统、发票平台、资金流水系统全部 mock。
- 保留外部动作按钮，但只更新前端状态和操作记录：
  - “模拟提交 OA”：单据状态变为审批中，生成审批节点和待办提示。
  - “模拟审批通过/驳回”：切换审批状态，释放或写入占用/核销中金额。
  - “模拟银行支付”：生成支付建议号、实际支付日期，可切换支付成功或支付失败。
  - “模拟同步 CBS”：更新同步状态、最近同步时间、同步批次号；失败时展示失败原因和重试入口。
  - “模拟生成凭证”：生成凭证号，例如 `KD-202605-0013`。
  - “模拟资金流水回写”：仅用于投放账户实际消耗金额/现金余额展示，不接真实流水。
  - “模拟导出”：toast 提示已生成导出任务，不创建真实文件。
- 不连接真实银行、CBS、OA、ERP、金蝶、广告平台，不上传真实附件，不发起真实付款。

## UI/UX 重点

- 整体按财务 B 端后台设计，突出核算主体、供应商、合同/结算单、应付余额、本次付款金额、支付状态和凭证号。
- 付款管理工作台作为入口，使用摘要指标 + 待办表格 + 异常列表，帮助演示人员快速进入闭环。
- 单据页按“申请信息、业务来源、结算/预付/投放明细、付款信息、附件、审批记录、操作日志”分区。
- 明细区和台账表格要支持横向滚动，固定单据编号、供应商/投放账户、金额、状态等关键列。
- 金额统一右对齐、千分位展示；付款金额、应付余额、未核销金额、充值差异金额要能快速比较。
- 状态标签明确：草稿/未同步为默认，审批中/支付中/核销中为处理中，支付成功/已完成为成功，已驳回/支付失败/同步失败/存在差异为警示或失败。
- 显隐规则要让业务含义清楚：选择有合同/无合同、无票/有票、已核销/未核销后，只展示当前路径必需区块。
- 金额超额、供应商不一致、无合同大额预付、退款金额超余额、重复选择等错误要在表格行内或字段旁直接提示。
- 附件只展示 mock 文件名、上传人、上传时间和状态，不做真实上传、预览或下载。
- 空状态提供“新建申请”或“重置筛选”；错误状态提供“重试同步”“发起重付”等下一步动作。

## 验收标准

- 页面名称、核心字段、表单分区、显隐规则、台账字段和台账更新关系与原始详细设计保持一致。
- 至少跑通“供应商应付账款台账 -> 对公付款申请 -> 提交审批 -> 审批通过 -> 模拟支付成功 -> 应付台账累计已付款金额更新”的闭环。
- 至少跑通“对公预付款申请 -> 审批通过 -> 供应商预付款台账插入 -> 后续付款单预付区可选择核销”的闭环。
- 至少跑通“投放账户充值申请 -> 财务付款 -> 审批通过 -> 投放账户余额/明细台账更新”的闭环，并能展示充值差异样例。
- 至少跑通“支付失败 -> 退票重付申请 -> 审批通过 -> 重付成功”的异常闭环。
- 对公付款单能根据是否有合同、是否无票、是否已发票核销切换业务区块，并完成必填和金额超额校验。
- 预付款申请能校验预付金额大于 0、5 万以上必须关联合同、无合同需关联营销事项。
- 投放退款能校验退款金额不超过充值余额。
- 提交、审批通过、驳回、支付成功、支付失败、生成凭证、同步失败等状态均可前端模拟并有操作日志。
- 外部系统行为全部为 mock，不发生真实银行、CBS、OA、ERP、金蝶、广告平台或附件上传调用。
- 核心页面具备 normal、loading、empty、error 或失败提示状态。
- UI 风格统一、稳定，适合 B 端后台现场演示。
- 开发完成后执行项目约定检查，优先 `npm run build`；如无法执行，记录原因。
